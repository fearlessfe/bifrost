## Overview

DashScope is Alibaba Cloud's model service (Bailian / Model Studio), home of the Qwen model family. Bifrost's DashScope provider mixes two protocol surfaces:

- **OpenAI-compatible chat** - Chat Completions, streaming, tool calling, and the Responses API run through DashScope's `/compatible-mode` surface via Bifrost's shared OpenAI converters.
- **Native audio & images** - TTS and image generation use the native DashScope protocol (`/api/v1`), which compatible-mode does not cover.
- **Speech transcription** - `qwen3-asr-flash` runs through compatible-mode chat completions with the audio as an `input_audio` content block; DashScope has no Whisper-style `/audio/transcriptions` endpoint.

### Supported Operations

| Operation | Non-Streaming | Streaming | Endpoint |
|-----------|---------------|-----------|----------|
| Chat Completions | ✅ | ✅ | `/compatible-mode/v1/chat/completions` |
| Responses API | ✅ | ✅ | `/compatible-mode/v1/chat/completions` |
| Speech (TTS) | ✅ | ✅ | `/api/v1/services/aigc/multimodal-generation/generation` |
| Transcriptions (STT) | ✅ | ❌ | `/compatible-mode/v1/chat/completions` (input_audio) |
| Image Generation | ✅ | ❌ | `/api/v1/services/aigc/multimodal-generation/generation` (qwen-image, z-image) or task API (wan) |
| Image Edit | ✅ | ❌ | `/api/v1/services/aigc/multimodal-generation/generation` (qwen-image-edit) |
| List Models | ❌ | ❌ | - |
| Embeddings | ✅ | ❌ | `/compatible-mode/v1/embeddings` |
| Batch | ❌ | ❌ | - |

## Models

| Family | Example models | Surface |
|--------|----------------|---------|
| Chat (Qwen) | `qwen-plus`, `qwen-max`, `qwen3-max` | compatible-mode (OpenAI protocol) |
| TTS | `qwen-tts`, `qwen3-tts-flash`, `qwen3-tts-instruct-flash` | native |
| ASR | `qwen3-asr-flash` | compatible-mode chat completions (input_audio) |
| Image (sync) | `qwen-image`, `qwen-image-plus`, `qwen-image-edit`, `z-image-turbo` | native |
| Image (async tasks) | `wan2.2-t2i-flash`, `wan2.2-t2i-plus`, `wanx2.1-t2i-turbo`, `wanx2.1-t2i-plus`, `wan2.5-t2i-preview` | native task API (submit + poll) |

Models whose name starts with `wan` are served through the asynchronous task API; Bifrost submits the task and polls it to completion, so the request stays synchronous from the client's perspective and may run for minutes. Set `network_config.default_request_timeout_in_seconds` accordingly (300 is a sensible default for image tasks).

## Setup & Configuration

<Tabs>
<Tab title="Web UI">

1. Navigate to **Models** > **Model Providers**. Look for **Alibaba DashScope** under **Configured Providers**. If it is missing, click on **Add New Provider** and select it.
2. Click **Add Key** or edit an existing key.
3. Set a name for your key.
4. Paste your DashScope API key directly or use an environment variable (for example, `env.DASHSCOPE_API_KEY`).
5. Set **Allowed Models** to **All Models** (default) or the specific model allowlist you want this key to serve.
6. Save the provider configuration.

## Speech (TTS)

Bifrost's `/v1/audio/speech` maps onto the qwen-tts family. The voice comes from the standard `voice` parameter; the audio format follows `response_format` (for example `mp3`, `wav`, `pcm`). Non-streaming responses return the synthesized audio inline (Bifrost downloads it from the upstream's 24-hour URL).

```bash
curl -X POST http://localhost:8080/v1/audio/speech \
  -H "Authorization: Bearer $BIFROST_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "dashscope/qwen3-tts-flash",
    "input": "今天天气真不错，我们出去走走吧。",
    "voice": "Cherry",
    "response_format": "wav"
  }'
```

Streaming returns base64 audio chunks as they are synthesized.

## Transcriptions (STT)

DashScope has no Whisper-style transcriptions endpoint, so Bifrost converts the uploaded file into a chat completion for `qwen3-asr-flash`: the audio bytes ride a single user message as a base64 `input_audio` content block, and the assistant's reply text comes back as the transcript. The client-facing request is unchanged; the audio format is inferred from the filename extension unless `file_format` is set explicitly.

DashScope's ASR options (`language`, `enable_itn`, ...) are non-standard: send them as extra form fields (or `extra_params.asr_options` in JSON) together with the `x-bf-passthrough-extra-params: true` header, and they are flattened onto the chat request body upstream as `asr_options`.

```bash
curl -X POST http://localhost:8080/v1/audio/transcriptions \
  -H "Authorization: Bearer $BIFROST_KEY" \
  -F "model=dashscope/qwen3-asr-flash" \
  -F "file=@audio.mp3"
```

## Image Generation

`qwen-image*` / `z-image*` models answer synchronously. Prompt-quality knobs such as `watermark` and `prompt_extend`, and DashScope-only values, can be passed through `extra_params`; a size in OpenAI notation (`1024x1024`) is converted to DashScope's `1024*1024` automatically.

```bash
curl -X POST http://localhost:8080/v1/images/generations \
  -H "Authorization: Bearer $BIFROST_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "dashscope/qwen-image",
    "prompt": "一只在茶园里奔跑的柯基犬，水彩风格",
    "size": "1024x1024",
    "extra_params": {
      "watermark": false,
      "prompt_extend": true
    }
  }'
```

`wan*` / `wanx*` models run through the asynchronous task API with the same request shape; note `negative_prompt` moves from `parameters` to `input` upstream and Bifrost handles that mapping for you.

## Qwen-specific chat parameters

Chat runs over compatible-mode, so qwen-specific knobs are flattened onto the request body. On the standard inference routes (`/v1/chat/completions`) they go directly at the top level; on the OpenAI integration routes (`/openai/v1/...`) they nest under `extra_params`:

```json
{
  "model": "dashscope/qwen-plus",
  "messages": [{"role": "user", "content": "你好"}],
  "enable_thinking": false,
  "top_k": 50
}
```

Thinking models reject `enable_thinking: true` on non-streaming calls; enable it only with `"stream": true`.
